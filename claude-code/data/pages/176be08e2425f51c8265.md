 Workspace-Scoped Resources 

 Every resource in Next-Gen Trust Security belongs either to a workspace or to the tenant as a whole. Which one it is decides whether the resource is still there after you switch workspaces, and whether you can change it when it is. 

 Resources That Belong to a Workspace 

 Each of these resources has one owning workspace. Under Tenant you see all of them and a Workspace column names the owner of each row. Inside a workspace you see only that workspace's, and the column is dropped because every row would say the same thing. 

 Certificates and Certificate Requests 

 Certificate Installations and TLS Server Endpoints 

 Issuer Certificates and Signing Keys 

 Machines, Kubernetes Clusters, and Cloud Keystores 

 Credentials 

 ACME Servers, SCEP servers, and ACME Orders 

 Built-in Accounts 

 Notification Rules and Custom Reports 

 Event Logs 

 Auto Renewal settings are workspace-scoped as well, though there is no column to show it: each workspace configures its own renewal window and provisioning behaviour, and one workspace's settings have no effect on another's. 

 Resources That Belong to the Tenant 

 Configuration that describes the tenant rather than a team stays at the tenant level. Most of the pages that manage it are available only when Tenant is selected, and they are listed in Workspace Availability by Page . What those pages define still applies inside every workspace: a certificate tag or an approval rule created under Tenant is in force everywhere, you just cannot maintain the list from inside a workspace. 

 VSatellites work differently from both groups, and this is the one that surprises people. The VSatellites page keeps its menu entry in every workspace, but a VSatellite is tenant infrastructure rather than a workspace's property. Inside a workspace the page is read-only: you can see the VSatellites and their status, but deploying, upgrading, and configuring one all require switching back to Tenant . 

 Licensing also reports at tenant level, with a usage breakdown by workspace. 

 Dashboards Follow the Selected Workspace 

 The TLS Certificates dashboard and the 47-Day Validity Readiness dashboard are available in every workspace, and each one reports on the workspace you have selected. Under Tenant they cover the whole tenant, including the certificates held by every workspace; inside a workspace they cover that workspace. Neither dashboard has a workspace filter of its own, so switching workspaces is how you change what they report on. 

 Certificates Are Claimed, Not Assigned 

 A certificate has three states, not two. It can be unclaimed, it can belong to the tenant, or it can belong to a workspace. Nothing moves a certificate out of the unclaimed state on its own — network discovery is configured at the tenant level, and what it finds arrives unclaimed and stays that way until somebody claims it. 

 Where you are decides what you can do: 

 From Tenant , select certificates and use Assign to Workspace to assign them to any workspace, to reassign ones that already belong to a workspace, or to unassign them. 

 From inside a workspace, you can claim unclaimed certificates into that workspace and release ones it already holds. You cannot take a certificate from another workspace. 

 A certificate belongs to one workspace at a time. Assigning a claimed certificate to a second workspace from Tenant moves it rather than adding an owner, and there is no way to give two workspaces a claim on the same certificate. A certificate can still be visible in two workspaces, which is what sharing a machine does, but visibility and ownership are different things: the Workspace column names the owner, and only the owner can release the certificate. You can assign up to 100 certificates in a single operation. 

 Claiming is governed by its own permission set, Assign Certificates to Tenants , which is separate from the Certificates permission set and grants nothing else. A Superuser holds every permission set and can always claim. For anyone else, create a custom role, add this permission set to it, and assign the role: no other predefined role includes it, and a role that can already work with certificates cannot claim them without it. 

 Note: The permission set is named Assign Certificates to Tenants , not Workspaces, so look for it under that name. 

 Kubernetes Clusters are the exception to "nothing claims a certificate for you". When you connect a cluster, you choose whether to leave the certificates it discovers unclaimed so that other workspaces can claim them, or to have the connecting workspace claim all of them automatically. 

 Sharing Makes a Resource Visible Elsewhere 

 Several resources can be shared with other workspaces, which gives those workspaces read-only access without changing who owns the resource. In the resource's own settings, this is the Authorized Workspaces field, or Authorize all workspaces to include every workspace, including ones created later. 

 Sharing is available for Request Policies, Issuance Policies, Issuer Sub CA Providers, Cloud Providers, Cloud Keystores, Credential Managers, trust bundles, and Machines. 

 Note: Sharing a machine also shares what that machine finds. A certificate discovered on a machine shared with two workspaces appears in both, without either one claiming it. 

 Notification Rules reach across workspaces in a different way. A rule created under Tenant has a Workspace scope setting that decides whether it evaluates events from workspaces as well as from the tenant, and whether it applies to all workspaces or only to the ones you name. The setting appears only when you are working under Tenant on a rule the tenant owns; a rule created inside a workspace covers that workspace alone. 

 Pages You Can Read but Not Change Outside the Tenant 

 These pages stay in the menu in every workspace, but some or all of what they do is reserved for Tenant . 

 Page What changes outside Tenant 

 VSatellites Read-only. 

 Request Policies Read-only. 

 Cloud Providers Read-only. 

 Trust Management Read-only. 

 Issuance Policies You can view policies, but not create or delete them. 

 Issuer Sub CA Providers You can view providers, but not create or delete them. The CA account name is shown as plain text instead of a link, because Certificate Authorities is available only under Tenant . 

 Cloud Keystores You cannot delete a keystore that another workspace owns. 

 This is not a permissions model. A user who can select Tenant can do all of it, so use a custom role, not a workspace, to keep somebody out of a page.
