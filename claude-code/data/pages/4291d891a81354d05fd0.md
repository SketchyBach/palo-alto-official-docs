SPIFFE identities for Google Cloud workloads and AI agents
NEW
August 10, 2026

With this update, Secure Workload Access (SWA) extends SPIFFE workload identity support to AI agents running on Google Gemini Enterprise Agent Platform (formerly Vertex AI). NEW

Simplified roles for the machine identities, AI agents, and secrets inventories
CHANGED
August 6, 2026

The roles required to access the machine identities, AI agents, and secrets inventories have been updated. Three roles now replace the previous access model:

Machines Admin — Provides full access to the data stored and displayed in the inventories, including external API queries and mutations, and onboarding operations.
Machines External Data Contributor — Provides write access to the inventories through the external API, allowing third-party services to contribute data without the ability to read inventory data or access remediation settings. For example, a custom integration that sends data from an unsupported provider.
Machines Internal Data Contributor — Provides access to the inventories through the internal data ingestion service, allowing internal services such as the Kubernetes Discovery Agent and cloud scanners to upload data.

If you previously assigned the Discovery & Context roles to your users, you must reassign them using the new roles.

Account updates from Privilege Cloud sync with lower latency
NEW
August 5, 2026

With this update, account updates from Privilege Cloud are available in Secrets Manager SaaS with lower latency through event-driven synchronization.

Account creations, property updates, and deletions sync shortly after they occur in Privilege Cloud.
Password rotations from the Central Policy Manager (CPM) and Secrets Rotation Service (SRS) are also synced shortly after they occur in Privilege Cloud.
No configuration changes are required. The enhancement applies automatically.

This feature is available in eu-west-2.

New command path parameters are required for SSH Keys platforms
CHANGED
August 2, 2026

Starting with version 20.1.0 of Unix SSH and version 21.0.0 of SSH Keys platforms, you must define the SuCommandPath or SudoCommandPath parameter at the platform level to configure the command path used by the plugin. At least one of these parameters is required; without it, the plugin does not operate.

New platform imports automatically include these parameters with a default value of /bin/su, which is valid for most Linux distributions. You can edit this value during setup to accommodate *NIX distributions that use non-standard binary paths.

If you upgrade an existing platform, you must manually add one of these parameters to keep the platform functional and avoid service interruptions.

Windows WMI plugin now requires PowerShell, FQDN, and domain accounts
CHANGED
August 2, 2026

Windows WMI plugin version 21.0.1 introduces updated requirements that change previous plugin behavior. Review the following requirements before you upgrade, to ensure compatibility and avoid service disruption.

The plugin now uses PowerShell cmdlets (CIM/WinRM) instead of the deprecated wmic.exe tool, for encrypted data transmission and long-term Windows compatibility.
You can no longer connect using a raw IP address. Use the fully qualified domain name (FQDN) for platform assignment and certificate mapping.
You must configure both a Logon account and a Reconcile account, using valid Domain User accounts. Local accounts are not supported.

For more information, see Windows Local Accounts with WMI.

Access policies for MCP tool execution
NEW
August 2, 2026

As a Secure AI admin, you can now restrict the tools that AI agents are allowed to run, so each agent only has access to the tools it actually needs.

Access policies control which AI agents can run which tools on your registered MCP servers. Each policy brings together three things: the users or roles allowed to initiate a session, the AI agents they operate through, and the specific tools on specific MCP servers those agents can run.

Access is denied by default. The system allows a tool request only when an enabled policy explicitly permits it, and records every attempt in the audit log.

For details, see Create an AI agent access policy.
