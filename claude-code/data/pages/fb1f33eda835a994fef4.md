 DLP harmonization 

 Beta 

 This feature is currently in beta and subject to change. 

 DLP harmonization is the process by which Cortex connects to your DLP providers, extracts their policy configurations, and restructures the provider-specific data into a single normalized schema. These normalized policies are stored in the Cortex Data Inventory as assets . Because every provider's fields are mapped to the same schema, you can compare, filter, and sort policies from all of them in one inventory through the Unified Policies page . 

 Cortex currently harmonizes DLP policies from two providers: 

 Provider 

 What it covers 

 Cortex Endpoint DLP 

 Data-in-motion enforcement on managed endpoints (USB, printers, local applications, web uploads). 

 Microsoft Purview 

 Microsoft 365 DLP across Exchange Online, SharePoint, OneDrive, and Teams. 

 Additional providers are planned for future releases. 

 The Unified Policies page 

 The harmonized results are presented on the Unified Policies page, at Modules → Data Security → Data Loss Prevention → Unified Policies . This page is the single inventory of every DLP policy Cortex has ingested. 

 The following image shows the Unified Policies page: 

 Widgets across the top summarize policy counts by status, connected providers, the most common data profiles, and coverage by channel. Below them, a table lists every normalized policy, one row per policy, filterable and exportable on any field in the schema. 

 Selecting a row opens a side card with two tabs: 

 Overview pairs an AI-generated summary of what the policy does with its properties, description, and the origins it monitors. 

 Configuration lists the policy's rules in priority order. Expanding a rule shows its own AI-generated summary and its detection conditions, which you can read either as a visual AND/OR/NOT tree or as code. 

 The table displays only a default selection of fields as columns; use Display to add or remove them. The side card shows the full set. 

 The page comes with the Data Security offering, but only policies from connected providers appear in the inventory, and each provider has its own requirements. See Connecting your DLP providers for details. 

 The inventory is read-only. To change how a policy behaves, edit it in the provider that owns it. Cortex re-scans each connected provider every 24 hours, picking up new, updated, and deleted policies without user intervention. A policy deleted upstream disappears from the inventory on the next scan. Each row's Last scanned field records the most recent successful pull, so check it before treating a row as authoritative for a recent change. 

 Data profiles marked as irrelevant to your environment are omitted from the inventory. Change this in the data profile settings, not in Unified Policies. 

 Connecting your DLP providers 

 Each provider has its own requirements and connection method. If you disable a connector, its policies remain in the inventory but are no longer updated. Because Cortex removes any asset that has not been seen for 30 days, those policies are deleted 30 days after the last successful scan. 

 Cortex Endpoint DLP 

 Ingesting Endpoint DLP policies requires any XDR license in a bundle that includes XDR Runtime, plus either the PAN-XDR-EP-DLP or PAN-XSIAM-EP-DLP add-on. 

 Onboarding is zero-touch. Cortex verifies the license at tenant provisioning and on every license-change event; once the check passes, it registers Endpoint DLP automatically and policies begin appearing in the inventory. 

 Enforcing DLP on endpoints is separate from viewing the resulting policies on the Unified Policies page. Enforcement requires the Cortex agent, which needs a base product such as Enterprise Runtime Security (Cortex XDR) in addition to the Endpoint DLP add-on. See Cortex Data Loss Prevention (DLP) module overview . 

 Microsoft Purview 

 Onboarding Purview requires the Global Administrator role in your Azure tenant and the ability to run a script in Azure Cloud Shell. 

 Onboard Purview through the Microsoft Security Connector at Settings → Data Sources . The wizard walks you through selecting Purview, enabling the Policies Discovery capability, running a generated script in your Azure environment, and entering the resulting credentials.  Policy vs. rule hierarchy 

 "Policy" does not mean the same thing in every provider's model, and the schema preserves the difference. Each row in the Unified Policies table is always a whole policy, never one of the rules inside it. Rules are shown in the Configuration tab of the side card. 

 Microsoft Purview nests multiple named rules inside a policy, each with its own priority, conditions, severity, and action. The Configuration tab lists them in priority order. 

 Cortex Endpoint DLP treats the policy and the rule as one object, so its Asset name is the rule name and the Configuration tab grays out the fields that would repeat. 

 Policy-level fields 

 Field 

 Description 

 Provider 

 The vendor that supplied the policy. 

 Type 

 The provider and its policy model, such as Microsoft Purview DLP Policy. 

 Category 

 Always DLP Policy. 

 Class 

 Always Security Services. 

 Asset name 

 The name given in the source provider, such as "Prevent Financial Data Transfer". 

 Asset ID 

 The unique Cortex identifier for the policy asset. Use it to reference a specific policy in a query. 

 Mode 

 Active, Inactive, or Simulation. A policy in Simulation is evaluated and logged but enforces nothing. 

 Priority 

 The evaluation order. When an event matches several policies, the provider applies them in this order to resolve the conflict. 

 Description 

 The intent or regulatory purpose, as written in the source provider. 

 Channels 

 The pathway or exit vector the data travels through: Web, Email, Cloud Drive, Endpoint, Messaging, or Gen AI. 

 Origins 

 The monitored workloads or applications where the data originates. Unlike Channels, these are not a fixed set of values; they are the workload names the provider reports, such as Exchange, SharePoint, OneDrive, Teams, Devices, or Browser. 

 Data Profiles 

 The Cortex data profiles that correspond to the sensitive data the policy detects, such as credit card numbers, Social Security numbers, or HIPAA data. Aggregated across all rules in the policy. 

 Audience Scope 

 Who the policy is enforced on, such as specific users, Microsoft 365 distribution groups, Entra administrative units, or endpoint device groups. 

 First Discovered 

 When Cortex first ingested the policy. 

 Last Scanned 

 When Cortex last pulled the policy from the provider. 

 Created 

 When the policy was created in the source provider. 

 Created By 

 The administrator who created the policy upstream. 

 Last Modified 

 When the policy last changed in the source provider. 

 Modified By 

 The administrator who last changed the policy upstream. 

 Every policy has a value for Mode , Priority , Channels , and Origins . The remaining fields are populated only if the source provider supplies them, so they can be empty. 

 Audience Scope is displayed alongside the origin it applies to. In the Overview tab, the Origins table pairs each origin with its audience and lists any excluded users or groups in a separate Exclusions column. 

 Category and Class are identical on every row, because every row is the same kind of asset. They matter only when querying the asset inventory more broadly, where they separate DLP policies from your other asset types. 

 Rule-level fields 

 Field 

 Description 

 Rule name 

 The name of an individual rule nested within the policy. 

 Rule ID 

 The unique Cortex identifier for the rule. 

 Provider rule ID 

 The identifier the source provider uses for the rule. Use it to match a rule back to its definition in the provider console. 

 Rule description 

 The intent or logic of an individual rule, as written in the source provider. 

 Rule priority 

 The evaluation order of an individual rule within the policy. 

 Mode 

 The status of the individual rule: Active, Inactive, or Simulation. A rule can be in a different mode than its parent policy. 

 Data Profiles 

 The sensitive data a specific rule looks for. 

 Action 

 The response the provider executes on a match, normalized across providers: Block, Block with Override, Generate Alert, Notify End User, or None. 

 Provider Severity 

 The severity the administrator set in the source provider, from Critical to Informational, used to prioritize the resulting alerts. 

 Access Scope 

 Whether the rule triggers on internal or external data movement.
