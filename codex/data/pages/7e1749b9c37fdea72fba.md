# Enable provisioning policies

Enable provisioning policies

This topic describes how to enable and configure provisioning policies in Idira Identity Governance and Administration (IGA). It covers how provisioning policies function, how to access the Policies page, and how to create or edit provisioning policies in your tenant.

Before you begin

Ensure that the custom actions feature is enabled in your organization to configure custom HTTP integrations.

How provisioning policies work

Provisioning policies bind each event to an ordered set of provisioning actions to automate user lifecycle events. The custom actions feature enables you to register outbound HTTP integrations in the action library and include them in your policies to invoke external systems without building a dedicated connector.

When the system detects a lifecycle event for a user, such as a directory synchronization, it evaluates all enabled policies that match the event type. If user conditions are met, a policy workflow starts for that user.

A policy workflow performs the following steps:

Creates a parent provisioning request for the user.

Runs prerequisite actions sequentially.

Runs actions in parallel after all prerequisites complete.

Waits until each action completes and then advances to the next step.

Records completion or failure for each step.

If multiple enabled policies match the same user and event, the system selects the first matching policy. Design policies so that only one policy applies to a given user and event.

Provisioning policies orchestrate lifecycle automation. They do not replace other provisioning paths, such as approved access requests, access review revocations, or time-bound access expirations. These paths can create fulfillment work directly.

Create or edit a provisioning policy

Use the following procedure to create or edit a provisioning policy in your tenant.

In the Idira IGA web portal, go to Provisioning > Policies.

Click Create Policy, or click the edit icon on an existing policy.

Configure the policy using these instructions:

Step 1: Policy information

Enter the basic details for the policy:

Policy Information fields

Field

	

Description




Name

	

A unique name for the policy.




Description

	

Enter an optional summary of the policy's purpose.




Lifecycle Event

	

The event that triggers this policy. Available events depend on your tenant configuration.




Category

	

Automatically derived from the lifecycle event: joiner, mover, or leaver. The category determines which actions are available.

Step 2: Configure the policy

Configure the following three sections:

Users: Define which users the policy applies to by adding attribute filters. If you do not configure any attributes, the policy applies to all users who trigger the matching lifecycle event. All configured conditions must match for the policy to apply.

To limit a joiner policy to active users, enter `userStatus` is not `inactive` or `deleted`.

Prerequisites: Prerequisites run serially, one at a time, in the order listed. Use prerequisites for steps that must complete before others begin. Click + Add Action to add a prerequisite, and from the drop-down, select the action type. Some actions require additional configuration, such as selecting a target application or custom action.

Actions: Actions run in parallel after all prerequisites complete. Use this section for steps that can run at the same time. Click + Add Action to add an action, and from the drop-down, select the action type.

Step 3: Enable the policy

Use the toggle to enable or disable the policy. A policy must be enabled to run when a matching lifecycle event occurs.

Click Submit.

Standard provisioning actions

The action library includes standard actions that cover common joiner, mover, and leaver scenarios. Standard actions cannot be edited or deleted.

Standard provisioning actions

Action

	

Description




Create Account

	

Creates a new account for the user in the selected application.




Disable Account

	

Deactivates the user's account in the selected application while retaining its data.




Disable User Accounts

	

Deactivates all of the user's active application accounts.




Provision Birthright Access

	

Grants access based on matching, active birthright profiles.




Request Additional Access

	

Sends an approval task to the user's manager for access beyond the birthright profile.




Revoke All Application Access

	

Removes all application access and permissions and deactivates all accounts.




Revoke Outlier Access

	

Removes access that is not covered by the user's matching birthright access.




Revoke Outlier Access in Application

	

Removes access that is not covered by the user's matching birthright access for the selected application or applications.




Wait for Account

	

Pauses the workflow until the selected application creates the user's account.




Wait

	

Pauses the workflow for a specified number of days before proceeding.




Invoke Custom Workflow Action

	

Runs a custom HTTP action configured in the action library. This action is available when the custom actions feature is enabled.

Custom actions

Custom actions enable organization administrators to register outbound HTTP integrations in the action library and include them in provisioning policies. Use custom actions when you need to call an external API that is not covered by a standard action, such as triggering a ServiceNow workflow to provision a laptop, notifying an HR system, or invoking an internal automation platform.

Custom actions in the Action Library are different from custom actions in Settings > Custom Actions, which are used for findings and rules automation, including email, Slack, Teams, and webhook notifications. This section covers only provisioning policy custom actions.

Overview

A custom action defines:

An HTTP method and endpoint URL

Optional URL parameters mapped from user attributes

Optional request headers

A request body template with dynamic user attribute values

Authentication credentials

A failure policy that controls whether the workflow continues if the call fails

When a policy workflow reaches an Invoke Custom Workflow Action step, the system performs three operations. It resolves the endpoint and body from the subject user's data, applies authentication, and sends the outbound HTTP request. Outbound calls are protected by HTTPS enforcement, server-side request forgery (SSRF) protection, and DNS pinning.

Create a custom action

Go to Provisioning > Policies and select the Actions tab.

Click Create Action to open the action wizard.

Configure the action using these steps:

Step 1: API configuration
API Configuration fields

Field

	

Description




Name of Action

	

A unique name for the action. This name appears when you add the action to a policy.




Description

	

Enter an optional description of the action.




HTTP Method

	

The HTTP method for the API call: GET, POST, PUT, PATCH, or DELETE.




API Endpoint

	

The full HTTPS URL of the target API. You can include dynamic placeholders using curly braces: `https://api.example.com/users/{userId}/provision`.




Configure URL Parameters

	

If your endpoint contains placeholder tokens, map each placeholder to a user attribute. Placeholders are resolved and URL-encoded at runtime.




Headers

	

Optional static HTTP headers to include with the request. Header values must be literal; dynamic header templating is not supported in this release.




Keep running if this action fails

	

Controls the failure policy. When enabled (default), the policy workflow continues even if the HTTP call fails. When disabled, a failed call stops the workflow.

Step 2: Authentication

Select an authentication type for the outbound API call:

Authentication types

Authentication type

	

Description




No Authentication

	

No credentials are sent.




Custom Headers

	

Authentication is provided through static headers you configure.




Basic Authentication

	

Username and password are sent as an HTTP Basic Authorization header.




OAuth 2.0—client credentials

	

Client ID, client secret, token URL, scopes, and content type are used to obtain an access token using the OAuth 2.0 client credentials grant.

Sensitive values, such as passwords and client secrets, are stored securely and returned in obfuscated form when you retrieve the action configuration.

Only the OAuth 2.0 client credentials grant is supported. Authorization code, implicit, refresh token, and user-delegated OAuth flows are not supported.

Step 3: API payload

Define the request body sent to the external API:

Upload a JSON file, or paste the request body directly.

Use JSONata expressions to map user attributes into the payload. Prefix attribute paths with `$.zillaUser`, such as $.zillaUser.email, $.zillaUser.displayName, or $.zillaUser.metadata.department.

You can use JSONata expressions for conditional logic, for example, assigning a device type based on the user's department:

{
  "email_address": "$.zillaUser.email",
  "display_name": "$.zillaUser.displayName",
  "device_type": "$.zillaUser.metadata.department = \"Engineering\" ? \"Mac\" : \"Windows\""
}

GET requests do not send a request body.

Step 4: Preview and validate

Select a sample user to preview the resolved endpoint parameters and payload. Verify that attribute mappings resolve to the expected values.

Click Submit.

Add a custom action to a policy

Create or edit a policy and go to Step 2: Configure Policy.

In Prerequisites or Actions, click + Add Action.

From the action drop-down, select Invoke Custom Workflow Action.

From the second drop-down, select your custom action, such as Provision Laptop.

Save and enable the policy.

Attribute mapping reference

At execution time, custom actions resolve templates using a JSONata context that includes the subject user's information:

{
  "zillaUser": {
    "id": "...",
    "email": "...",
    "displayName": "...",
    "department": "...",
    "metadata": { }
  }
}

Description

Failure handling

When a custom action's HTTP call fails, the outcome depends on the Keep running if this action fails setting:

Failure handling options

Setting

	

Behavior




Enabled (default)

	

The failure is logged and recorded on the workflow action. The policy workflow continues to the next step.




Disabled

	

The failure is recorded and the policy workflow stops.

Failure details, including HTTP status and response body when available, are recorded in the workflow action's `failureReason` field. You can view these details on the provisioning dashboard and through workflow APIs.

Monitor policy execution

After a lifecycle event triggers a policy, you can monitor progress on the Provisioning dashboard. The dashboard displays the following details:

Lifecycle events and their processing status

Policy workflow progress

Individual action status, including failure reasons for custom actions

Tenant administrators can also manually start, stop, or inspect policy workflows through the provisioning APIs.
