Outbound traffic requirements - Static configuration (General environment)

The ISPSS components and Idira Identity Connector communicate through the internet with the Idira cloud environment through specific FQDNs and ports which ensure that all their communication is secure and according to the Idira protocol.

This topic presents the static FQDNs, ports and protocols that should be configured according to organizations with a static configuration policy.

This topic presents configuration requirements for a non-FedRAMP environment.

If you require configuration details for a FedRAMP-compliant environment, work according to the steps in Outbound traffic requirements (FedRAMP environment).

Static communication configuration

Static configuration refers to the use of:

the hostname of each component and port or IP of each component and port

-or-

the IP of each component and port

We do not recommend static configuration because the cloud infrastructure dynamically scales to support platform operations. Hardcoding static parameters requires manual adjustments whenever services expand or shift, which creates a high risk of connection timeouts and service unavailability. If you must implement a static configuration, use fully qualified domain names (FQDNs) instead of IP addresses to ensure continuous routing.

If your organization enables Dynamic configuration using wildcard-based dynamic firewall rules, see Outbound traffic network and port requirements - Dynamic configuration.

Idira Identity Connector configuration

All connections to the internet made by Idira Identity (including the Idira Identity Connector and mobile management) are outbound in nature. No internet facing ingress ports are required. All outbound connections are made via TCP to either port 80 or 443 and should not have any restrictions.

The destination resource, IP address, and host for outbound connections may vary over time and should be updated for new or canceled resources.

Static configuration for Idira Identity Connector

If adding domain names to an allow list is not possible, and you can only use IP addresses, contact Technical Support for the relevant IP addresses for your tenant.

Use of deep packet inspection filtering of HTTPS or SSL traffic by web proxies or security software may cause connectivity issues with Idira Identity. In all cases, the ports and addresses discussed below should be excluded from packet inspection to allow for normal service operation.

Additional steps

When applying static configuration, you are required to open additional IP addresses or FQDNs for specific third parties.

Open CloudFront/EC2 IP ranges (General regions) 

Open CloudFront IPs or EC2 IPs according to the AWS region where your Idira tenant is hosted:

Open amazonaws ip ranges and search for IP instances that contain both of the following parameter settings:

"service": "CLOUDFRONT" or "service": "EC2", depending on the service you want to enable.

"region": "<region>" for every instance where <region> is the region where your Idira tenant is hosted. For example, us-east-1.

For each relevant result of your service and region combination, note the IP range found under "ip_prefix", and open all the IP ranges found in that search.

For example:

For more information, see AWS IP address ranges.

Open the AWS certificate FQDNs (General regions)

Amazon Trust services maintains multiple certification authorities, each of which could be the certificate issuer of your certificate, when it is issued and at renewal.

Open your organization's certificate OCSP Responder and CA issuers to extract their AWS FQDN addresses:

OCSP Responder

CA issuer

Extract the details for each certificate in the chain.

In the Privilege Cloud portal, click the View site information icon > Connection is secure > Certificate is valid.

In the Certificate Viewer window click Details and in the Certificate Hierarchy pane, click each of the certificates in the chain and in Certificate Fields click the following certificate fields:

Authority Information Access

CRL Distribution Points

and extract the URL address that appears in the Field Value display.

Copy the OCSP Responder and CA Issuer URLs and configure these FQDNs in your firewall to support Idira AWS SSL.

Repeat these steps for each certificate in the chain and whenever you renew a certificate, to ensure all certificate FQDNs are whitelisted in your firewall.
