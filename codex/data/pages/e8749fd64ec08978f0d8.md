> For the complete documentation index, see [llms.txt](https://docs.koi.ai/llms.txt). Markdown versions of documentation pages are available by appending `.md` to page URLs; this page is available as [Markdown](https://docs.koi.ai/integration-guides/prisma-airs-runtime-enforcement.md).

# Prisma AIRS - Runtime Enforcement

Koi extends its protection to the content flowing through AI coding agents by integrating with Prisma AIRS, Palo Alto Networks' AI runtime security service (see the [Prisma AIRS documentation](https://docs.paloaltonetworks.com/ai-runtime-security) to learn more). Where Koi governs the endpoint - what agents run, where they run, and what they're allowed to do - Prisma AIRS inspects the actual content of the prompts, tool calls, and responses moving through those agents. Together we provide hermetic AI security across SaaS, cloud, and local endpoints, so organizations can adopt Cursor, Claude Code, and similar agents at scale without expanding their attack surface.

This integration uses the **Prisma AIRS AI Runtime API -** Koi calls the Runtime API's scan endpoint to inspect the text inside a prompt, tool call, or model response, and the API returns a single verdict (allow or block) along with masked text where sensitive data is detected. It detects threats including prompt injection, sensitive data leakage, insecure output (such as malware and malicious URLs), toxic content, and credential leakage.

These detection rules are grouped into **security profiles**, which are defined and managed entirely within the Prisma AIRS console (Strata Cloud Manager). Koi consumes the verdict; it never sees or changes how a detector is configured.

### Koi Support for Prisma AIRS

Koi provides native support for Prisma AIRS as a **Protection Profile**, a new integration category built for external verdict sources, of which AIRS is the first. By connecting AIRS and attaching it to a runtime policy, you can enable AIRS-powered inspection at the endpoint without deploying or maintaining hooks on individual devices.

The two products own opposite halves of enforcement, and the boundary is strict: **AIRS inspects content, and Koi deals with the endpoint-level deployment, enforcement and end-user communication.**

* **Prisma AIRS owns detection and verdict.** It inspects each intercepted prompt, tool call, and response, and returns the block/allow decision.
* **Koi owns enforcement, deployment, and visibility.** It decides which agents and endpoint groups to protect and which events to intercept, deploys and manages the AIRS hooks on every device (with API keys handled centrally), enforces the returned verdict, and attributes every verdict to a device, agent, policy, profile, and detector.

Detection rules are defined once in the AIRS SCM portal, and Koi pushes enforcement to thousands of endpoints as managed policy, replacing a manual, per-device hook model that collapses at enterprise scale.

#### Interception points

Koi can forward the following AI-agent events to AIRS Scan API:

* **Prompts**: before a prompt reaches the LLM.
* **MCP tool calls**: before execution, scoped to external MCP tools.
* **Network calls**: `WebFetch` and `WebSearch`, before and after.

Built-in tools are excluded initially for latency reasons.

Each of these is also a rule type in Koi's runtime policies. For which agents support Prompts, MCP tools, and Network rules - and the per-agent exceptions that apply - see [Runtime policy rule types](https://docs.koi.ai/guides/agentic-runtime-control/agent-enforcement-custom-policies/runtime-policy-rule-types#supported-agents).

### Security profiles

A **security profile** is the unit of detection configuration in Prisma AIRS. It defines which detectors run, their actions (for example, prompt injection set to *block*), and the latency threshold and fallback. Profiles are created and maintained in the Prisma AIRS console; see [Create and Configure an API Security Profile](https://docs.paloaltonetworks.com/content/techdocs/en_US/ai-runtime-security/administration/api-intercept-create-configure-security-profile).

After you connect the integration, Koi fetches your profile list so you can reference profiles by name in a policy - Koi never edits a profile's detectors.

A policy applies profiles at two levels:

* **Default profile (policy level):** selected with the **Apply protection profile** action. Applies to every rule.
* **Custom profile (per rule):** any rule (prompt, MCP tool, or network) can override the default. The override applies to that rule only.

At runtime, each event is scanned against the matched rule's custom profile if set, otherwise the policy default. This lets one policy scan prompts, tool calls, and network requests against different profiles without splitting into several policies.

### Configuring the Integration

Configuration spans two portals. The first three steps happen in **Prisma AIRS (Strata Cloud Manager)**; the remaining steps happen in the **Koi console**. The only two values copied by hand between them are the service-account credential and your region's API endpoint; everything else Koi fetches programmatically.

#### Step 3: Create a runtime policy

On the **AI Runtime policy** page, click **Create policy**. Runtime policies gain a new action alongside the existing **Block** and **Ask - Apply protection profile**:

* **Block / Ask** (existing): Koi detects the match *and* decides the outcome.
* **Apply protection profile** (new): Koi forwards the matched event to a protection profile, which detects *and* returns the verdict. Koi enforces and records that verdict through its existing hook mechanism, with no Koi-side decision on top.

Configure the policy by setting its **scope** (which agents and endpoint groups it applies to), its **rules** (the events to intercept: prompts, MCP tools, network calls), and its **action** (**Apply protection profile**, then select the API key and security profile Koi fetched in Step 2). The profile dropdown shows your actual AIRS profiles, prefixed by source, for example *Prisma AIRS · prod-injection-dlp-strict*.

On save, the policy is pushed to every in-scope endpoint, where the Koi agent enforces it locally.

> **Note:** An AIRS profile may be scoped to specific agents. If a Koi policy targets more agents than the selected profile covers, scope the two to match so every targeted agent is protected as expected.

### Runtime Execution

Once a policy is live, every matched event makes a round trip through AIRS without interrupting the developer. For example, when a developer pastes client PII into an AI agent prompt:

1. The Koi managed hook fires on the prompt event *before* it leaves the endpoint and calls the [AIRS Scan API](https://pan.dev/prisma-airs/api/airuntimesecurity/scan/scans/) at the API endpoint configured for your region.
2. AIRS runs the profile's detectors and returns a **block** verdict with the masked text.
3. Koi enforces the verdict, blocking the action and showing a message to the end user in the Cursor chat.
4. The event flows to the Koi console, correlated to the agent's session timeline.

If the AIRS API is unreachable, hooks **fail open** to the profile's fallback configuration and do not retry, so a network hiccup never blocks a developer.

### How AIRS Verdicts Appear in Koi

Koi records every AIRS verdict in the **agent runtime inventory**, alongside the endpoint and agent activity it already tracks. Each session opens to its agent, endpoint, and actions, and the events timeline records every intercepted call.
