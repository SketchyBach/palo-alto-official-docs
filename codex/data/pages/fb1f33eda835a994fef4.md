 DLP Harmonization 

 Beta 

 This feature is currently in beta and subject to change. 

 DLP harmonization is the process by which Cortex connects to your DLP providers, extracts their policy configurations, and restructures the provider-specific data into a single normalized schema. In the broader Cortex inventory, these normalized policies are treated as assets . Because every provider's fields are mapped to the same schema, you can compare, filter, and sort policies from all of them in one inventory. 

 Cortex currently harmonizes DLP policies from two providers: 

 Provider 

 What it covers 

 Cortex Endpoint DLP 

 Data-in-motion enforcement on managed endpoints (USB, printers, local applications, web uploads). 

 Microsoft Purview 

 Microsoft 365 DLP across Exchange Online, SharePoint, OneDrive, and Teams. 

 Additional providers are planned for future releases. 

 The Unified Policies page 

 The harmonized results are presented on the Unified Policies page, at Modules → Data Security → Data Loss Prevention → Unified Policies . This page is the single inventory of every DLP policy Cortex has ingested. 

 The following image shows the Unified Policies page: 

 Widgets across the top summarize policy counts by status, connected providers, the most common data profiles, and coverage by channel. Below them, the Unified Policies table lists every normalized policy, one row per policy, filterable and exportable on any field in the schema. 

 Selecting a row opens a side card with two tabs: 

 Overview pairs an AI-generated summary of what the policy does with its properties, description, and the origins it monitors. 

 Configuration lists the policy's rules in priority order. Expanding a rule shows its own AI-generated summary and its detection conditions, which you can read either as a visual AND/OR/NOT tree or as code. 

 The page comes with the Data Security offering, but only policies from connected providers appear in the inventory, and each provider has its own requirements. See Connecting your DLP providers for details. 

 The inventory is read-only. To change how a policy behaves, edit it in the provider that owns it. Cortex re-scans each connected provider every 24 hours, picking up new, updated, and deleted policies without user intervention. A policy deleted upstream disappears from the inventory on the next scan. Each row's Last scanned field records the most recent successful pull, so check it before treating a row as authoritative for a recent change. 

 Connecting your DLP providers 

 Each provider has its own requirements and connection method. If you disable a connector, its policies remain in the inventory but are no longer updated, and Cortex removes them after 30 days of inactivity. 

 Cortex Endpoint DLP 

 Ingesting Endpoint DLP policies requires any XDR license in a bundle that includes XDR Runtime, plus either the PAN-XDR-EP-DLP or PAN-XSIAM-EP-DLP add-on. 

 Onboarding is zero-touch. Cortex verifies the license at tenant provisioning and on every license-change event; once the check passes, it registers Endpoint DLP automatically and policies begin appearing in the inventory. 

 Enforcing DLP on endpoints is separate from viewing the resulting policies on the Unified Policies page. Enforcement requires the Cortex agent, which needs a base product such as Enterprise Runtime Security (Cortex XDR) in addition to the Endpoint DLP add-on. See Cortex Data Loss Prevention (DLP) module overview . 

 Microsoft Purview 

 Onboarding Purview requires the Global Administrator role in your Azure tenant and the ability to run a script in Azure Cloud Shell. 

 Onboard Purview through the Microsoft Security Connector at Settings → Data Sources . The wizard walks you through selecting Purview, enabling the Policies Discovery capability, running a generated script in your Azure environment, and entering the resulting credentials. For the full procedure, see <<Link to Microsoft Purview configuration article>>. 

 Policy vs. rule hierarchy 

 "Policy" does not mean the same thing in every provider's model, and the schema preserves the difference. Every row is a policy, never a rule. 

 Microsoft Purview nests multiple named rules inside a policy, each with its own priority, conditions, severity, and action. The Configuration tab lists them in priority order. 

 Cortex Endpoint DLP treats the policy and the rule as one object, so its Asset name is the rule name and the Configuration tab grays out the fields that would repeat. 

 The normalized schema 

 Normalization maps every provider's fields onto a single schema, allowing you to query and filter policies across all connected providers simultaneously—whether you are filtering locally on the Unified Policies page or querying assets more broadly across Cortex. 

 Within the Unified Policies page, every field in the schema is filterable and appears in the side card. The table displays only a default selection of these fields as columns; use Display to add or remove them. 

 The Level column in the table below shows which object a field relates to: 

 Policy — the information in the field relates to the entire policy. 

 Rule — the information in the field relates to the rules within the policy. If a policy contains multiple rules, it has multiple values for this field. The Unified Policies table combines them into a single cell, using a + n chip for any that don't fit. The Configuration tab breaks them out individually per rule. 

 Policy & Rule — the information in the field relates to both the policy and its rules, with separate values. The Unified Policies table row shows the policy's; the Configuration tab shows each rule's.
