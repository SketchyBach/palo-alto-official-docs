 Access Management for New and Migrating Users 

 Next-Gen Trust Security (NGTS) uses Strata Cloud Manager (SCM) for access control. You manage who can access resources by assigning users to Tenant Service Groups (TSGs) and defining their permissions through roles. 

 This topic explains how access control works in NGTS. It also explains how NGTS access control differs from the approach in Certificate Management, SaaS. 

 How Access Management Works in NGTS 

 If you are new to certificate management in NGTS, your access is governed by two things working together: the Role you are assigned, and the Workspace scopes assigned alongside it. 

 Workspaces : A workspace is a named subset of your tenant's resources. Isolate business units, environments, or departments by creating a workspace for each one and assigning its scope to the people who work there. Creating a workspace needs no permission to create a tenant and no sharing of products or credits, and workspaces are flat, so there is no hierarchy to keep in step with anything else. See Workspaces Overview . 

 Explicit Instance Sharing : Activation does not cascade automatically. When NGTS is activated at the parent TSG level, administrators must explicitly share the instance with eligible child TSGs in their hierarchy to deploy the product. 

 The Data Region Constraint : For sharing to succeed, child TSGs must reside in the exact same data region (e.g., US-EAST) as the parent TSG. The system will prevent you from sharing NGTS with any child TSG located in a different data region to comply with data residency rules. 

 Centralized Licensing : License management and SCI usage counts are aggregated for the tenant as a whole. The Licensing page reports the tenant total and breaks consumption down in a Usage Breakdown by Workspace table. The page keeps its menu entry in every workspace, so which users see it is decided by their role, not by the workspace they have selected. 

 Roles : While you may see various predefined roles within the Strata Cloud Manager UI, access in NGTS is managed using two built-in roles: Superuser (full access) and View Only Admin (a guest role for read-only access). 

 IMPORTANT : When assigning the Superuser built-in role, you must strictly constrain it to the Next-Gen Trust Security application. Otherwise, the user will inadvertently be granted Superuser access to every application in your entire Strata platform. 

 The Access Equation : A user's actual permissions are the exact intersection of the role they are assigned and the workspace scopes assigned with it . The role decides what they can do; the scope decides which workspace they can do it in. For example, a user might have a role with full access to manage certificates, but they can only perform those actions in the workspaces they hold a scope for, and what they can do changes when they switch workspaces. 

 Resource Sharing and Visibility : Resource visibility follows the workspace you have selected. Tenant shows the resources of every workspace and is the only selection that does; any other workspace shows only its own, and there is no view that spans several workspaces. Tenant-level configuration such as Certificate Authorities (CAs) and request policies is created under Tenant , and a request policy must be shared through its Authorized Workspaces field before users in a workspace can request certificates with it. Code signing operates differently: when setting up a Signing Key in a workspace, users can select any supported CA created under Tenant (such as Built-in CA, DigiCert, ZTPKI, and MS ADCS) without an administrator making it available first. In all cases, users in a workspace can consume these shared request policies and CAs, but they cannot modify them or view the underlying CA configurations. Separate NGTS instances stay separate: if you activate NGTS for one tenant in the US and another in Germany, neither sees what is in the other. 

 If You’re Migrating from Certificate Manager, SaaS 

 If you are migrating from our legacy Certificate Management, SaaS (CM, SaaS) platform, the old authorization model based on flat teams and simple predefined roles has been completely replaced. 

 From "Inviting Users" to Enterprise Identity : In the past, managing tenants involved inviting other users to your tenant account. Now, user identity and tenant management are centralized within SCM. You manage users by binding them to Strata-managed roles and assigning them the scope of each workspace they work in. 

 The Removal of the "Applications" Feature : In CM, SaaS, the "Applications" feature was heavily used to group certificates and dictate which Resource Owners had access to them. In NGTS, the Applications feature has been entirely removed. Because of the improved RBAC approach, grouping by application is no longer necessary; instead, certificates are owned directly by a workspace, or by the tenant. 

 Resource Ownership and Assignment : Resources are no longer tied to individual user attributions (like the old createdBy fields). Instead, ownership is enforced at the workspace level through two primary scenarios: 

 Requested or Added Certificates : When a user explicitly adds or issues a certificate (e.g., creates a certificate request) in a workspace, that certificate is automatically owned by that workspace. 

 Discovered Certificates : Network discovery is configured under Tenant , and certificates it finds arrive unclaimed. Nothing moves them out of that state on its own. From Tenant , you can assign a certificate to a workspace, reassign one that already belongs to a workspace, or unassign it; from inside a workspace, you can claim unclaimed certificates and release the ones that workspace holds, but you cannot take a certificate from another workspace. A certificate has one owner at a time, and you can act on up to 100 in a single operation. Claiming is governed by the Assign Certificates to Tenants permission set ( ngts.certificate_assign ), which is named for tenants rather than workspaces. In a workspace, that permission also controls whether unclaimed certificates are visible: users without it see only the certificates their workspace owns. A Superuser holds every permission set and can always claim. For more, see Workspace-Scoped Resources . 

 Mapping Legacy Certificate Manager, SaaS Roles to NGTS Roles 

 Because the old predefined Certificate Manager, SaaS roles and Application groupings are retired, you will utilize Strata Cloud Manager's flexible RBAC capabilities to recreate and enhance your access policies. Here is how you can map your old workflows to the new NGTS environment: 

 Legacy Certificate Manager, SaaS Role NGTS Equivalent / Implementation 

 Admin / PKI Admin (Previously: Full read/write over all certs/settings) Tenant-level Superuser: Assign an administrator the built-in "Superuser" role with tenant-level access. This grants full read, write, and sharing capabilities across the tenant. These users can select Tenant , see and manage the resources of every workspace, and are responsible for sharing items like request policies with workspaces. There is no PKI Admin default role in NGTS. 

 Resource Owner (Previously: Could manage certs attached to Apps they owned) Workspace Superuser: Assign the user the built-in "Superuser" role together with the scope of a single workspace. That gives them full control over that workspace's resources, matching the legacy Resource Owner experience, and completely replaces the need for "Applications" assignments. They can consume resources the tenant has shared with the workspace. Because their access comes entirely from a workspace scope, they never see Tenant . 

 Guest / Read-Only (Previously: View access only) View Only Admin: Assign users to the built-in "View Only Admin" role. This grants read-only access across the environment and prevents them from accessing create, edit, or delete buttons in the UI, matching the legacy Guest read-only experience. 

 Service Accounts (Previously: Automated API access and integrations) Strata Service Accounts vs. NGTS Built-in Accounts: If your legacy Resource Owners utilized service accounts in Certificate Manager - SaaS, you must now choose the correct account type based on your integration needs. Use Strata service accounts to invoke NGTS APIs (which pass through the Strata API gateway). Conversely, use NGTS built-in accounts strictly for product-delivered integrations that communicate directly with the NGTS data plane and generally involve non-public APIs. 

 Activating NGTS Across Your Organization's TSG Hierarchy 

 When your organization is ready to start using Next-Gen Trust Security, you must initiate the activation process from the top of your tenant hierarchy. Once activated on the parent TSG, you must then explicitly share the NGTS instance with your eligible child TSGs to deploy the product across your various business units. 

 Prerequisites 

 You must be assigned a Customer Superuser role within Strata Cloud Manager (SCM). 

 Your organization's parent TSG must already be created in Strata Cloud Manager (SCM). Child TSGs do not need to be present before activating the parent; they can be created at a later date and granted access through explicit instance sharing at that time. 

 To Activate NGTS Across Your TSG Hierarchy 

 Log in to Strata Cloud Manager and ensure you are operating within the parent TSG. 

 Activate the NGTS product instance on the parent TSG. 

 Explicitly share the NGTS instance with your eligible child TSGs. 

 To do this, navigate to the Activation console and select the parent TSG where NGTS was activated using Secure-Flex Credits. On the far right of the tile representing the NGTS instance, click the vertical ellipses to reveal a menu. Select the option to share the instance, and when the modal pops up, select the new child TSGs to share the NGTS instance with. Ensure that the child TSGs you intend to share with are located in the exact same data region (e.g., Americas) as the parent TSG to comply with data residency rules. 

 Verify that the instance was successfully shared. 

 Adding a New Child TSG to an Active NGTS Environment 

 As your organization grows and new departments or environments require isolation, you can seamlessly expand your NGTS footprint. Once NGTS is actively running on your parent TSG, you can create new child TSGs in your hierarchy and explicitly share the NGTS instance with them to instantly bring the new business units into the NGTS ecosystem. 

 Prerequisites 

 The parent TSG must already have NGTS activated. 

 You must have administrative access in Strata Cloud Manager to create new tenant structures. 

 To Add a New Child TSG 

 Create the new child TSG within Strata Cloud Manager (SCM) directly under your activated parent TSG. 

 Ensure the new child TSG is created in the exact same data region (e.g., Americas) as the parent TSG to comply with data residency rules and allow NGTS capabilities to be successfully shared. 

 Explicitly share the NGTS instance with the new child TSG. To do this, navigate to the Activation console and select the parent TSG where NGTS was activated using Secure-Flex Credits. On the far right of the tile representing the NGTS instance, click the vertical ellipses to reveal a menu. Select the option to share the instance, and when the modal pops up, select the new child TSG to share the NGTS instance with. 

 Note: Because cross-region data sharing violates data residency requirements, the system will strictly enforce this boundary. If a child TSG is in a different data region, the system will either prevent you from selecting it in the modal or display an error message. 

 Verify that the instance was successfully shared. 

 Monitoring SCI License Usage Across Your Organization 

 License consumption in NGTS is centralized to simplify administration. Rather than checking each workspace separately, administrators can track the aggregate Secure Credential Issuance (SCI) usage across the entire tenant from one page, ensuring streamlined billing and centralized oversight. 

 Prerequisites 

 You must have a Customer License Administrator or Superuser role. 

 NGTS must be actively consuming licenses. 

 To Monitor SCI License Usage 

 Log in to the system and select Tenant in the workspace switcher. 

 Navigate to the Licensing page in the UI. 

 Review the aggregate SCI usage count. This number represents the total, rolled-up consumption across the tenant and all of its workspaces. 

 To see which workspace is consuming what, review the Usage Breakdown by Workspace table, which lists each workspace and its metrics separately. 

 Note: The Licensing page is not restricted to Tenant — it keeps its menu entry in every workspace. Who can open it depends on whether their role includes the Licensing permission, not on which workspace they have selected.
